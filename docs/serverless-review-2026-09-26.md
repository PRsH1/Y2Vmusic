# 서버리스 이전 검토에 대한 2차 의견

검토일: 2026-09-26. 대상 문서: [serverless-feasibility-2026-09-26.md](./serverless-feasibility-2026-09-26.md) (Codex 작성).

이전을 검토한 이유는 현재 Oracle 인스턴스의 자원 부족이다. 동시 다운로드가 1개로 제한되고 변환이 느리다. 이 문서는 그 목적에 비추어 원 문서를 검토하고, 운영 서버 실측과 공식 문서로 주요 주장을 검증한 결과다.

**판정: 원 문서의 사실관계는 대부분 정확하지만, 권고 순서가 목적과 맞지 않는다.** 이전의 가부를 가르는 조건은 코드가 아니라 **Vercel(AWS) 출구 IP에서 YouTube 추출이 되는가** 하나다. 이는 문서나 코드로 판단할 수 없고 PoC 한 번으로 결정해야 한다. 코드 개편은 원 문서가 제시한 것보다 작게 할 수 있다.

## 검증한 것

### 운영 서버 실측 (VM.Standard.E2.1.Micro)

| 항목 | 결과 |
|---|---|
| 인스턴스 사양 | Oracle 공식 문서상 **1/8 OCPU** (burstable), 1GB |
| CPU steal | 부하 중 `vmstat` st **27~34%** — 하이퍼바이저가 CPU를 회수 중 |
| ffmpeg 벤치 (3분 사인파 → MP3 320k) | 서버 **11.44초** (user 6.81초) / 로컬 i7-13650HX **2.66초** |
| 실제 곡 (3:33) yt-dlp 추출, deno | 벽시계 16.43초, CPU 13.2초, 최대 RSS 284MB |
| 같은 곡, **node를 JS 런타임으로** (`--js-runtimes node`, deno 없음) | 벽시계 16.82초, CPU 12.9초, 최대 RSS 263MB — **정상 동작** |
| MP3 320k 변환 | 벽시계 20.26초, CPU 15.6초, 결과 8.5MB |
| FLAC 변환 | 벽시계 11.02초, CPU 6.4초, 결과 **47MB** |
| WARP 없이 Oracle IP 직접 다운로드 | **성공** (1회. 결론을 내리기엔 표본 부족) |

느린 원인은 코드가 아니라 인스턴스 형태다. 곡 하나에 CPU 약 29초가 드는 작업을 1/8 코어에서 돌리고 있다.

## 원 문서에 대한 의견

### 맞는 부분

- 일반 Workers에서 `child_process`가 동작하지 않는다는 점, 따라서 검색·정보·장르 차트까지 막힌다는 점.
- 프로세스 로컬 상태(`job-registry`, `admission`)가 다중 인스턴스에서 깨진다는 점.
- "4.5MB를 넘으니 불가능"이 부정확하다는 점, `500M`이 입력 제한일 뿐 작업 디렉터리 전체 제한이 아니라는 점.
- 서버리스가 반드시 싸다고 볼 수 없다는 경계, CORS가 인증이 아니라는 지적.

### 동의하지 않는 부분

**1. 1단계 권고(Vercel UI + Oracle 처리 서버)는 목적을 해결하지 않는다.**
느린 것은 추출·변환이고 UI 렌더링은 부하가 거의 없다. 분리해도 속도와 동시성은 그대로이고, 대신 두 출처·CORS·도메인 변경에 따른 localStorage(이력·설정) 유실이 생긴다. 원 문서도 "다운로드 자체의 속도 향상을 보장하는 이전은 아니다"라고 인정한다. 이 단계는 건너뛰는 것이 맞다.

**2. 가장 큰 위험이 검증 항목 중 하나로만 다뤄진다.**
WARP는 systemd 데몬이라 Vercel 함수에서 상주시킬 수 없다. 그리고 Vercel 함수의 출구는 AWS IP이며, YouTube는 클라우드 IP를 봇으로 막는 경우가 많다(이 프로젝트가 WARP를 도입한 이유). 직접 접속이 안 되면 대체 수단이 필요하다.

- 요청마다 사용자 공간 WireGuard 프로세스(wireproxy 등)를 띄워 WARP 경로를 재현 — **미검증**. `child_process`와 아웃바운드 UDP가 필요하다.
- 로그인 쿠키 — YouTube 계정 제재 위험.
- 유료 주거용 프록시 — 비용 발생.

이 조건이 통과되지 않으면 나머지 개편은 의미가 없으므로 **가장 먼저** 확인해야 한다.

**3. deno를 필수 의존성으로 가정했다.**
실측으로 node가 JS 챌린지 런타임으로 동작함을 확인했다. Vercel Node 런타임에는 node가 있으므로 yt-dlp 단일 바이너리와 ffmpeg 정적 빌드만 포함하면 된다. 합계 약 120MB로 250MB 표준 번들 안에 들어올 것으로 보이나, 실제 번들 크기는 배포로 확인해야 한다.

**4. 2단계 설계(지속 큐, lease/heartbeat, 객체 저장소, 만료 URL)는 개인용에 과하다.**
곡 단위 작업은 더 빠른 CPU에서 300초 안에 충분히 끝나므로 **"요청 하나 = 다운로드 하나" 구조를 유지할 수 있다.**

- 대기열·동시 실행 제한(`admission`)은 플랫폼이 인스턴스를 늘리므로 불필요해진다.
- 남는 문제는 진행률(`/api/status` 폴링이 다른 인스턴스로 갈 수 있음) 하나다. 클라이언트가 이미 응답 본문을 끝까지 읽어 Blob을 만들고 있으므로(`app/page.tsx`의 다운로드 처리), **진행률 이벤트를 같은 응답 스트림 앞부분에 프레이밍해 보내면** 공유 저장소 없이 해결된다. 폴링 요청 약 80회/건도 사라진다.
- 큐와 저장소는 3시간 영상 같은 긴 작업을 유지해야 할 때만 필요하다. 그 범위를 포기하면 필요 없다.

**5. 비용은 추정할 수 있다.**
위 실측에서 곡당 CPU는 느린 코어 기준 약 29초다. 더 빠른 vCPU에서는 줄어들 것으로 보고 곡당 15~30 CPU-초로 잡으면, Hobby 4 CPU-시간(14,400초)으로 **월 약 500~900곡**이 무료 범위다. 메모리는 2GB × 곡당 1분 미만으로 360 GB-시간에 여유가 있다. 추정치이므로 PoC에서 실제 Active CPU를 확인해야 한다.

### 원 문서가 다루지 않은 확인 항목

- **Fluid Compute의 인스턴스 내 동시성**: Fluid Compute는 동시 요청을 같은 인스턴스에 태울 수 있다. CPU를 쓰는 다운로드 두 개가 1 vCPU를 나눠 쓰면 동시성 이점이 줄어든다. PoC에서 동시 요청 2~3개로 확인한다.
- **리전**: 기본 `iad1`(미국 동부)이다. 사용자·YouTube 경로를 고려해 `icn1`(서울)로 지정하고, 리전별 차단 여부가 다를 수 있으므로 같이 확인한다.

## Vercel 단독 이전 시 변경 범위

| 항목 | 작업량 | 비고 |
|---|---|---|
| yt-dlp·ffmpeg 바이너리 포함 | 중 | Next.js는 `outputFileTracingIncludes` 사용. `--js-runtimes node` |
| yt-dlp 설정 파일 의존 제거 | 소 | 서버 `~/.config/yt-dlp/config`의 옵션을 코드 인자로 이동 |
| 임시 경로 `process.cwd()/temp` → `os.tmpdir()` | 소 | 500MB. 기동 스위퍼는 의미 없어짐 |
| 진행률을 응답 스트림에 포함, `/api/status`·`job-registry` 제거 | 중 | 클라이언트 파서 변경 |
| `admission` 제거 또는 인스턴스 내 제한으로 축소 | 소 | Fluid 동시성 결과에 따름 |
| 길이 상한 3시간 → 1시간 안팎 | 소 | Hobby 300초. 정확한 값은 PoC 실측. 기능 축소 |
| 차트·info 캐시 인스턴스별 분산 | 소 | 기능 영향 없음, 외부 호출 증가 |
| **WARP 대체** | **미정** | PoC 결과에 따라 불필요 ~ 이전 불가 |

## 권고 순서

1. **PoC로 가부 결정.** `icn1`에 함수 하나를 올려 yt-dlp(node) + ffmpeg로 짧은 곡을 약 20회 받는다. 측정: 성공률, 벽시계·Active CPU, 동시 요청 시 속도, 번들 크기. Vercel 계정 연결과 배포는 사용자가 수행해야 한다(`npm i -g vercel`).
2. **통과 시**: UI 분리 단계 없이 Vercel 단독으로 이전한다. 변경 범위는 위 표.
3. **실패 시**: 서버리스 대신 VM 교체가 답이다. 현재 구조를 유지한 채 더 큰 VM으로 옮긴다. Ampere A1은 춘천 리전에서 제공되지 않으므로 다른 리전 또는 저가 유료 VPS가 대상이다.

## 이번 검토의 확인 범위

- 운영 서버에서 CPU·steal·추출·변환을 실측했다. 앱 코드와 운영 설정은 변경하지 않았다.
- WARP 없는 직접 다운로드 성공은 1회 표본이므로 운영 설정(WARP 사용)은 그대로 둔다.
- Vercel·Cloudflare·Google Cloud에 배포하거나 비용이 발생하는 리소스를 만들지 않았다. Vercel(AWS) IP에서의 YouTube 접근은 **검증하지 않았다** — 이 문서의 결론이 PoC를 요구하는 이유다.
