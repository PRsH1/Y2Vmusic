# 차트 최신성 검증 보고서

검증일: 2026-09-26 KST

## 결론

현재 구현은 저장해 둔 과거 순위를 영구 표시하는 방식이 아니다. 지정된 YouTube 플레이리스트를 조회하고, 성공한 결과를 서버 메모리에 2시간 캐시한다. 다만 **실시간 순위 서비스도 아니다.** 한국·일본·글로벌은 주간 Top Songs 차트이며, 나머지 장르 탭은 장르/분위기/연도별 선곡 플레이리스트다.

특히 **R&B 탭의 원본은 `Korean R&B Hits 2024`**다. 원본 설명도 2024년 한국 R&B 히트곡 모음이라고 명시한다. 해당 탭에서 오래된 곡이 반복되는 구체적인 원인으로 확인되었다. 최신 시점에 이 목록을 다시 조회해도 최신 R&B 인기 순위로 바뀌지는 않는다.

## 방법과 범위

- `CLAUDE.md`, 차트 설정, 서버 API, YouTube API/yt-dlp 래퍼, 캐시, 클라이언트 표시 코드를 읽었다.
- 운영 주소 `https://y2vmusic.duckdns.org`의 `/api/charts?id=...`를 직접 호출했다.
- 로컬 yt-dlp 2026.03.17로 12개 원본 플레이리스트의 이름, 설명, 소유 채널, 수정일, 영상 ID 배열을 조회했다. 미디어는 다운로드하지 않았다.
- 제목 번역·표기 차이의 영향을 피하도록 영상 ID와 순서, 전체 곡 수를 비교했다.
- SSH로 운영 서버의 관련 소스 6개 파일 SHA-256을 확인했다. `lib/playlists.ts`, `lib/chart-cache.ts`, `lib/youtube-api.ts`, `lib/ytdlp.ts`, `app/api/charts/route.ts`, `components/explore/explore-section.tsx` 모두 검증 당시 로컬 파일과 일치했다. 운영 Git HEAD는 `e9239f874786a3f43f40a5d2b355f5a48d645a55`였다.
- 서비스 코드·설정·배포는 변경하지 않았다. 검증 스크립트와 응답 스냅샷은 `docs/chart-audit-2026-09-26/`에 보관한다(최초 저장 위치는 `temp/` 였으나, 서버·로컬의 temp 스위퍼가 6시간 초과 항목을 삭제하므로 옮겼다).

원본의 소유 채널은 국가별 3개가 `YouTube Music Global Charts`, 장르별 9개가 `YouTube Music`으로 조회되었다. 국가별 원본 설명은 `This week's ranking of the most popular songs on YouTube.`였다. [YouTube 공식 도움말](https://support.google.com/youtube/answer/9014376?hl=en)도 Weekly Top Songs를 주간 차트로 설명한다.

12개 원본 모두 yt-dlp의 `modified_date`가 `20260925`로 조회되었다. **이 값은 플레이리스트 메타데이터의 수정일이며, 모든 곡이나 순위가 그날 변경되었다는 증거는 아니다.** 실제로 2024년 R&B 모음에도 같은 수정일이 붙어 있다.

R&B 운영 응답 상위 항목은 `DEAN - NASA (feat. FKJ)`, `LEEYOUNGJI - Small girl feat. DOH KYUNG SOO (D.O.)`, `BABYMONSTER - SHEESH`였다. 제목만 보고 발매일을 추정한 결론이 아니라, 원본 목록의 이름·설명·전체 50곡 대조에 근거한 판단이다.

## 갱신이 실제로 작동하는 방식

1. 화면 진입 또는 카테고리 클릭 시 `/api/charts`를 호출한다.
2. 해당 플레이리스트의 캐시 생성 후 2시간이 지나지 않았으면 메모리의 결과를 반환한다.
3. 2시간이 지난 뒤 다음 요청이 들어오면 캐시를 삭제하고 YouTube를 새로 조회한다.
4. 성공한 결과를 다시 2시간 캐시한다. 원본 조회 실패 시 500 오류를 반환하며, 만료된 캐시를 대신 반환하는 분기는 없다.

즉, **2시간마다 실행되는 수집 스케줄러가 아니라 요청이 들어올 때 만료 여부를 확인하는 캐시**다. 원본이 바뀌어도 기존 캐시의 남은 유효기간 동안은 이전 결과를 볼 수 있다. 페이지를 계속 열어놓으면 별도 자동 재조회가 없으므로 화면의 기존 결과가 더 오래 남을 수 있다.

근거:

- [캐시 TTL과 만료 처리](../lib/chart-cache.ts): 3, 12–31행
- [API 캐시/조회 분기](../app/api/charts/route.ts): 37–78행
- [최초 조회와 카테고리 클릭](../components/explore/explore-section.tsx): 148–177행

API는 `dynamic = "force-dynamic"`이며 응답의 `Cache-Control`은 `no-store`다. 운영 응답에서도 해당 헤더를 확인했다. 차트 데이터베이스, 정적 곡 목록, 장기 저장된 순위 파일을 읽는 경로는 없다. 고정으로 저장된 값은 곡 순위가 아니라 **플레이리스트 ID**다.

## 확인된 표시·메타데이터 문제

### 장르별 숫자는 공식 순위가 아니다

`lib/ytdlp.ts:171`의 `rank: index + 1`은 플레이리스트에서 읽은 순서에 번호를 붙인다. `components/explore/explore-section.tsx:203`은 장르 탭까지 `showRank`를 켠다. 인기 지표나 집계 기간을 조회해 순위를 계산하는 처리는 없다.

국가별 차트도 `lib/youtube-api.ts:76`에서 읽은 순서대로 번호를 붙이지만, 원본 자체가 주간 순위 목록이므로 그 순서를 반영한다. 모든 장르 목록에 같은 의미를 적용할 수는 없다.

### `cachedAt`은 실제 수집 시각이 아니다

`app/api/charts/route.ts:43`은 캐시 적중 시에도 `new Date().toISOString()`을 넣는다. 내부 캐시의 최초 저장 시각을 반환하지 않는다.

운영 한국 차트를 반복 호출했을 때 100곡의 ID와 순서는 같았지만 `cachedAt`은 아래처럼 달라졌다.

- `2026-09-25T18:43:45.511Z`
- `2026-09-25T18:43:52.305Z`

따라서 `cachedAt`으로 원본이 방금 갱신되었는지 판단할 수 없다. 현재 화면은 이 필드를 표시하지 않으므로, 이 오류가 화면의 곡 순서를 바꾸지는 않는다. 실제 수집 시각과 원본 차트의 집계 기간을 구분할 메타데이터가 부족한 상태다.

## 검증의 한계 및 추가 관찰

- 이번 조사는 한 시점의 코드와 운영 응답 검증이다. 지난 몇 달의 순위 이력이 없으므로 과거에 특정 곡이 어느 주에 어떻게 이동했는지는 입증하지 않았다. 오래된 곡이 주간 차트에 남아 있다는 사실만으로 캐시 장애라고 판단할 수 없다.
- OST와 트로트는 로컬 원본이 각각 100곡까지만 조회되었고 운영 응답은 135곡·103곡이었다. 공통 100곡의 순서는 일치했다. 뒤에 붙은 35곡·3곡의 최신성 및 조회 환경에 따른 곡 수 차이의 원인은 확정하지 않았다. 전체 일치로 집계하지 않았다.
- 일부 장르의 첫 운영 조회에서 20초 또는 50초 제한 내 응답을 받지 못했으나, 후속 조회에서는 12개 탭 모두 HTTP 200을 확인했다. 이것은 조회 지연 관찰이며, 원본 순위가 오래되었다는 증거는 아니다. 원인은 이번 조사에서 확정하지 않았다.

## 권장 개선

1. 국가별 탭을 `한국 주간 Top 100`처럼 실제 집계 주기에 맞게 표시한다.
2. 장르 탭을 선곡/추천 목록으로 구분하고, 숫자를 순위처럼 표시하지 않거나 목록 순서임을 명시한다.
3. R&B의 2024년 모음을 현재 목적에 맞는 원본으로 교체한다. 인디 탭의 `Seoul Cafe` 연결도 의도에 맞는지 재검토한다.
4. 원본 이름·링크, 실제 수집 시각, 가능한 경우 차트 집계 기간을 표시한다. `cachedAt`은 최초 캐시 저장 시각으로 바로잡는다.
5. 화면 복귀/일정 시간 경과 시 재조회하고, 서버 캐시와 원본의 갱신 주기를 구분해 안내한다.

기능 수정이나 배포는 수행하지 않았다.
